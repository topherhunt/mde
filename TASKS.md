- **Finder Quick Look previews of** `.md` **files -- answer one question first: can an ad-hoc-signed appex register at all?** MDE has no Quick Look support today (the `CFBundleDocumentTypes` block in `forge.config.ts` is the unrelated "can open this file type" declaration), so spacebar in Finder shows macOS's own raw-source plain-text preview. Adding it means a native Swift app extension -- an `NSViewController` conforming to `QLPreviewingController`, in an `.appex` bundle under `MDE.app/Contents/PlugIns/`, rendering markdown independently of TipTap (probably `WKWebView` over generated HTML, i.e. a second renderer to maintain). Toolchain is *not* the obstacle: verified 2026-08-16 that full Xcode is unnecessary and everything needed is already installed -- `swiftc` 6.1.2, `QuickLookUI.framework` in the CLT SDK, `pluginkit`, `lsregister` -- since an appex is just a plist plus a Mach-O linked with `-e _NSExtensionMain`. The blocker is signing, and it is pass/fail: appex bundles must be signed inside-out with their own entitlements (so `postPackage`'s `codesign --deep` would have to be restructured, carefully -- that hook is what stands between us and a "damaged, move to Trash" app), extensions are generally required to be sandboxed, and it is unverified whether LaunchServices will activate an extension whose host app carries only an ad-hoc signature and lives outside `/Applications`. Since a paid Developer ID cert is off the table, that last point decides the whole feature, so spend an hour on a throwaway hello-world appex that previews any `.md` as a fixed gray box: if it appears on spacebar the rest is just rendering work, and if it doesn't the idea is dead. Note there is no way to E2E test any of this -- the extension runs in `QuickLookUIService`, out of Playwright's reach, so it would be hand-checked every release.

- **BUG, DATA LOSS: opening and saving a file DELETES every image in it.** Verified 2026-08-01 with a throwaway E2E probe, not inferred. Open a file containing `![a cat](cat.png)`, make any edit, hit Cmd+S, and the file on disk comes back with the image line gone -- silently, with no warning, for both local and `https://` images. Cause: the editor has no image node in its schema at all (`Editor.tsx` loads StarterKit, which does not bundle `@tiptap/extension-image`, and nothing adds it). So markdown -> HTML produces an `<img>`, ProseMirror's parser finds no matching node type and drops it on the floor, and serializing the resulting document back to Markdown writes out a file that never had an image in it. Nothing recovers it except the file's checkpoint history.

  **A warning is now in place** (2026-08-01): opening a file that contains image syntax raises a blocking dialog naming the file, counting the images, quoting each reference verbatim, and saying that saving will remove them. It is fence-aware and code-span-aware, so a file *documenting* Markdown does not trigger it. That is a stopgap that buys time -- it does not save anybody's images, and it should be deleted in the same change that fixes level 1 below.

  Two levels of fix, and they are worth separating:
  1. **Stop the destruction** (small, urgent). Add `@tiptap/extension-image` so the node simply *exists* in the schema and survives the load -> save round trip. Even if it renders as a broken-image icon, the Markdown is preserved, which is the part that actually matters. Needs an E2E test that round-trips a file with an image and byte-compares -- the kind of test that should have existed all along.
  2. **Make images actually work** (bigger, optional). Does a *relative* path resolve against the file's own folder the way links do, or against the app bundle (broken icon for every local image)? Do remote images load or does Electron's CSP block them? And there is no way to *insert* one: no toolbar button, no drag-and-drop, no paste-an-image-from-the-clipboard. That is a real feature, not a bug fix.
